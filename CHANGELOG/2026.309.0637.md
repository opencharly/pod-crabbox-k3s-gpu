# 2026.309.0637 — feat(image): add the NVIDIA-GPU k3s lease image pod-crabbox-k3s-gpu

## Summary

Creates `opencharly/pod-crabbox-k3s-gpu`, the W5.2 NVIDIA-GPU variant of the k3s CachyOS
lease image, and lands its first commit. The image is `pod-crabbox-k3s:2026.309.0459` plus
the NVIDIA userspace, the toolkit's CDI refresh made runnable inside a lease, and the device
plugin that advertises `nvidia.com/gpu`.

The repo carries the seven files the sibling image repos carry — `charly.yml`, one candy,
the CI image caller, `AGENTS.md`, `README.md`, `CHANGELOG/.gitkeep`, `.gitignore` — and no
runtime code. `.github/workflows/tag-on-merge.yml` is already on `main`: it was installed by
the org bootstrap, not by this PR.

**What the GPU delta is, and why each part is the shape it is:**

1. **The GPU userspace is required, not re-declared.**
   `require: '@github.com/opencharly/layer-nvidia:v2026.296.0940'` is the one implementation
   of `nvidia-container-toolkit` + `nvidia-utils` + the Vulkan ICD wiring. The repo declares
   no GPU package of its own, so there is one place to fix a distro arm (R2). The tag resolves
   to commit `6141d493760683acc38595765646411dccebb06b`, which is an ancestor of that repo's
   `origin/main` (`git -C layer-nvidia merge-base --is-ancestor 6141d493760683acc38595765646411dccebb06b origin/main`, exit 0).

2. **The refresh unit is enabled by the PACKAGE, so the image adds no `enable` step.** The
   Arch `nvidia-container-toolkit` 1.20.1 package ships
   `/usr/lib/systemd/system/multi-user.target.wants/nvidia-cdi-refresh.{path,service}` as
   vendor symlinks. Re-linking them here would be a second copy of the package's own work.

3. **A container cannot satisfy the vendor unit's `ExecCondition`, so a drop-in clears it.**
   The vendor unit gates on
   `ExecCondition=/bin/sh -c '/usr/bin/grep -qE "/(nvidia|nvidia-current)[.]ko" /lib/modules/%v/modules.dep || [ -e /dev/dxg ]'`.
   A lease runs the HOST kernel and carries no `/lib/modules/<release>` tree, so that grep can
   never match; a failing `ExecCondition` makes systemd **skip** the unit (not fail it), so no
   `/var/run/cdi/nvidia.yaml` would ever be generated and the device plugin would enumerate
   nothing. `/etc/systemd/system/nvidia-cdi-refresh.service.d/20-crabbox-lease.conf` resets the
   list with an empty `ExecCondition=` — `systemd.unit(5)`: *"If the empty string is assigned to
   this option, the list of commands is reset"*. This removes the vendor condition without
   copying and re-owning the vendor unit.

4. **The spec is refreshed, never snapshotted.** The unit's own
   `NVIDIA_CTK_CDI_OUTPUT_FILE_PATH=/var/run/cdi/nvidia.yaml` is asserted by a check. A
   one-shot `nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml` is the form
   CONTAINERD.md §14.2 rejects: the driver version appears throughout the generated spec, so
   the first driver upgrade breaks every CDI mount that names it.

5. **The device plugin is a k3s manifest, not a post-boot `kubectl apply`.** The DaemonSet
   lives at `/var/lib/rancher/k3s/server/manifests/nvidia-device-plugin.yaml`, which k3s
   reconciles at startup and on change. It pins `nvcr.io/nvidia/k8s-device-plugin:v0.20.1` and
   carries the row's three env vars — each a real v0.20.1 option, verified in the plugin's own
   source at that tag (`--device-list-strategy` / `DEVICE_LIST_STRATEGY`,
   `--nvidia-driver-root` / `NVIDIA_DRIVER_ROOT`, `--nvidia-cdi-hook-path` /
   `NVIDIA_CDI_HOOK_PATH`; `cmd/nvidia-device-plugin/main.go:131`). With
   `DEVICE_LIST_STRATEGY=cdi-cri` the allocation is handed to containerd as a CRI
   `CDIDevices` id, so a workload pod needs no `runtimeClassName`. The `driver-root` hostPath
   and the `/var/run/cdi` mount are the upstream chart's own mechanism for resolving NVML and
   the refreshed spec without an injected runtime handler.

**What this PR does NOT claim.** `charly check box` is a build-scope gate: it proves the
packages, the binaries, the units, the drop-in and every value in the manifest are present in
the built image. It does not boot the lease, generate a CDI spec, or run a workload pod.
Those are deploy-context claims and need a deploy-context bed; the image description and the
repo's `AGENTS.md` say so in those words rather than implying otherwise.
