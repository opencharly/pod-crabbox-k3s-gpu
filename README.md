# pod-crabbox-k3s-gpu

The **NVIDIA-GPU k3s CachyOS lease image** for the Crabbox `containerd` provider —
the [`pod-crabbox-k3s`](https://github.com/opencharly/pod-crabbox-k3s) control-plane
lease contract plus the NVIDIA userspace, the toolkit's CDI refresh, and the
device plugin that advertises `nvidia.com/gpu`.

## What it provides

Every lease contract property of the base image is inherited unchanged:

| Property | Value |
|---|---|
| Base | `ghcr.io/opencharly/pod-crabbox-k3s:2026.309.0459` (CachyOS) |
| SSH | `sshd` on **2222**, public-key only, user `crabbox` |
| Inputs | read-only `/crabbox`: `authorized_keys`, `lease.env`, `bootstrap.sh` |
| Readiness | `/usr/local/libexec/crabbox/ready` — polled over SSH until exit 0 |
| PID 1 | `/sbin/init` → `/usr/lib/systemd/systemd` |
| k3s | pinned `v1.37.0+k3s1` on the inner containerd, node-ip `172.31.255.1` |

This variant adds the GPU stack:

| Property | Value |
|---|---|
| Toolkit | `nvidia-container-toolkit` — `nvidia-ctk`, `nvidia-cdi-hook` |
| Driver userland | `nvidia-utils` — `nvidia-smi`, `/usr/lib/libnvidia-ml.so.1` |
| CDI spec | `/var/run/cdi/nvidia.yaml`, regenerated by `nvidia-cdi-refresh.path` / `.service` |
| Device plugin | `nvcr.io/nvidia/k8s-device-plugin:v0.20.1`, `DEVICE_LIST_STRATEGY=cdi-cri` |
| Resource | `nvidia.com/gpu`, allocated through the CRI's CDI field |

The toolkit's refresh unit ships **enabled by the package itself** (its
`multi-user.target.wants` vendor links). A lease is a container, so it has no
`/lib/modules/<release>/modules.dep` for the vendor unit's `ExecCondition` to
grep; this image adds a drop-in that resets that condition, which is what makes
the refresh run at boot instead of being skipped.

The spec is **refreshed, never snapshotted**: `nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml`
is a one-shot whose driver version appears throughout the file, so the first
driver upgrade breaks every CDI mount that names it. Only `/var/run/cdi` is
regenerated (CONTAINERD.md §14.2).

## How to use it

The provider runs this image as a `crun`/`runc` lease that has the NVIDIA GPU
devices attached. Inside the lease, k3s is already running with the device plugin
applied, so a plain pod gets a GPU:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-probe
spec:
  restartPolicy: Never
  containers:
    - name: c
      image: nvidia/cuda:12.6.0-base-ubuntu24.04
      command: ["nvidia-smi", "-L"]
      resources:
        limits:
          nvidia.com/gpu: 1
```

No `runtimeClassName` is needed: with `DEVICE_LIST_STRATEGY=cdi-cri` the plugin
hands containerd the allocated device as a CDI id and containerd injects it.

## Requirements and limits

- **The lease must be started with the GPU devices attached.** The image cannot
  attach a device to itself; the provider starts the lease with the NVIDIA CDI
  device, and the refresh unit then generates the spec from what the lease sees.
- **`nvidia-utils` is a ~1 GB installed userland.** It is not optional: the
  refresh unit's `ExecStart` runs `nvidia-smi -L`, and the device plugin loads
  `libnvidia-ml.so.1`.
- **The build proves artifacts, not a cluster.** `charly check box` verifies the
  packages, the binaries, the refresh units, the drop-in and every value in the
  device-plugin manifest. Whether the spec is generated at boot and whether a
  workload pod actually execs `nvidia-smi` are deploy-context claims and need a
  deploy-context bed.
- **Nothing in the image starts a VMM or a GPU.** k3s and the inherited inner
  containerd do the work; the host owns the device.

## Layout

- `charly.yml` — the `pod-crabbox-k3s-gpu` image (pinned base image, systemd
  entrypoint).
- `candy/nvidia-gpu-lease/` — the `layer-nvidia` requirement, the refresh-unit
  drop-in, the device-plugin DaemonSet and the `check:` steps that prove the row.
- `.github/workflows/image.yml` — builds on `pull_request` and publishes at the
  merge tag, so the image tag equals the git tag.
- `CHANGELOG/` — per-CalVer history.
